Audit of [`custom_components/babycam/www/webrtc-babycam.js`](../custom_components/babycam/www/webrtc-babycam.js) (working tree, 2026-07-01, ~4,321 lines) against
documented web-platform behavior: WHATWG HTML/DOM, CSSOM View, W3C WebRTC 1.0, MDN, and
Chromium platform documentation (web.dev, Chrome Platform Status, Page Lifecycle API).

listener & timer hygiene; network/storage/context APIs). Every raw finding was then
independently re-verified by an adversarial reviewer instructed to refute it against both the
actual code and the primary documentation. Findings that failed verification are listed in

### 1. isElementActuallyVisible() can never pass inside Home Assistant's nested shadow DOM (elementFromPoint retargeting)

**Area:** custom-elements-shadow-dom

**What the code does.** isElementActuallyVisible() (C:\Projects\ha-babycam\js\webrtc-babycam.js:3130-3165) decides visibility with `document.elementFromPoint(x,y)` and then `elementAtPoint === element || element.contains(elementAtPoint)`. Per CSSOM View, document.elementFromPoint never returns a node inside a shadow tree: the hit result is retargeted against the document, so for a card buried under HA's nested shadow roots (home-assistant → hui-root → view → card) it returns the outermost shadow host (effectively <home-assistant>), never the card or its descendants. Node.contains() is single-tree (not shadow-including), so the check is provably false for every point, every time, in every browser inside HA. Every code path that relies on this helper is dead: the proactive attach in connectedCallback (lines 3315-3326, whose own comment says it exists to fix black cards in browser_mod popups / fullscreen kiosk), and the visibilitychange resync (line 3176), which therefore always computes `false` and detaches an on-screen card before the recreated IntersectionObserver's async initial record re-attaches it.

**What the standard says.** CSSOM View resolution: elementFromPoint/elementsFromPoint 'should not return an element inside a shadow tree; ... the element found must be retargeted against the context object' (https://github.com/w3c/csswg-drafts/issues/556; conformance test http://wpt.live/shadow-dom/DocumentOrShadowRoot-prototype-elementFromPoint.html asserts document.elementFromPoint returns the shadow host). Node.contains is defined on 'inclusive descendant' in the same node tree, not shadow-including (https://dom.spec.whatwg.org/#dom-node-contains). MDN: elementFromPoint returns null for points outside the viewport (https://developer.mozilla.org/en-US/docs/Web/API/Document/elementFromPoint).

**Evidence.** webrtc-babycam.js:3157-3158: `const elementAtPoint = document.elementFromPoint(point.x, point.y); if (elementAtPoint === element || element.contains(elementAtPoint)) { return true; }` — element is `this` (<webrtc-babycam>), whose root is a shadow root, so elementFromPoint can never return it. Dependents: 3176 `this.isVisibleInViewport = this.isElementActuallyVisible(this);` (visibilitychange), 3322 same call inside the connectedCallback setTimeout whose comment (3316-3320) documents the intent to attach in popups/fullscreen kiosk.

**Recommended update.** Make the hit test shadow-aware: descend open shadow roots (`let hit = document.elementFromPoint(x,y); while (hit?.shadowRoot) { const deeper = hit.shadowRoot.elementFromPoint(x,y); if (!deeper || deeper === hit) break; hit = deeper; }`) then test composed containment by walking `hit` upward via `node.parentNode ?? node.host` and returning true if the chain passes through `element`. Equivalently, accept the retargeted result when it is a shadow-including ancestor of the card (walk element.getRootNode().host chain and compare against elementAtPoint). Keep the isConnected and computed-style checks unchanged; do not alter the background branches in applyVisibility or the attach/detach flow.

### 2. Live reconfiguration (setConfig on an existing card) leaves a visible card permanently detached/black

**Area:** custom-elements-shadow-dom

**What the code does.** The reconfig path detaches the card (applyVisibility(false,false) at line 3023) and re-runs connectedCallback (3026). connectedCallback → setupVisibilityAndResizeHandlers() finds the old IntersectionObserver still present (`if (!this.intersectionObserver)` at 3193) and does NOT re-observe, so per spec no new IntersectionObserver record will ever be generated while the card stays intersecting (records only fire on the initial observe() and on threshold crossings). The only remaining re-attach path is the setTimeout geometric check (3321-3324), which always returns false in HA (see finding 1) and additionally overwrites isVisibleInViewport to false. Result: reconfiguring a currently-visible card (e.g., every keystroke in the HA GUI card editor preview, which reuses the element and calls setConfig repeatedly) detaches it and it never re-attaches until the user scrolls it fully out and back in or switches tabs.

**What the standard says.** MDN IntersectionObserver.observe(): 'The observer callback will always fire the first render cycle after observe() is called' — and only again when intersection status crosses a threshold; an already-observed, still-intersecting target generates no further records (https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/observe).

**Evidence.** webrtc-babycam.js:3016-3028 (reconfig detach + manual connectedCallback), 3193-3196: `if (!this.intersectionObserver) { this.intersectionObserver = new IntersectionObserver(...); this.intersectionObserver.observe(this); }` — skipped because the observer survived applyVisibility(false); 3321-3324: `this.isVisibleInViewport = this.isElementActuallyVisible(this); if (this.isVisibleInViewport || this.session?.background) { this.applyVisibility(...) }` — never true in HA, and `this.session` is null after detach.

**Recommended update.** In the reconfig branch of setConfig (line ~3023), after applyVisibility(false, false) also reset this.isVisibleInViewport = false, and force a fresh initial observation before/inside the connectedCallback re-run: this.intersectionObserver?.disconnect(); this.intersectionObserver = null; so setupVisibilityAndResizeHandlers() re-creates and re-observes, which per spec guarantees a first-render-cycle record; with isVisibleInViewport reset to false, an isIntersecting=true record differs and drives applyVisibility(true) to re-attach. (Plain unobserve/observe also works but resetting isVisibleInViewport is required either way, otherwise the callback's change-detection at line 3183 no-ops if the initial record races ahead of the mount setTimeout.) Additionally, stop overwriting isVisibleInViewport at line 3322 when the result is not acted on — isElementActuallyVisible is structurally unreliable inside HA's nested shadow DOM because document.elementFromPoint retargets to the outermost shadow host. Note: the trigger is not the GUI editor preview on current HA (hui-card forces element re-creation when preview is set); it is any same-type config update delivered to a live dashboard card via hui-card._updateElement -> setConfig, e.g., saving an edited babycam card, which currently blacks out the visible stream until a full scroll-out/in or tab switch.

### 3. IntersectionObserver callback updates isVisibleInViewport before the document.fullscreenElement early-return, with no fullscreenchange resync

**Area:** custom-elements-shadow-dom

**What the code does.** intersectionObserverCallback() assigns `this.isVisibleInViewport = isIntersecting` and only then bails out if `document.fullscreenElement` is truthy, and no 'fullscreenchange' listener exists anywhere in the file to apply the deferred state later. Because subsequent IO records only trigger action when isIntersecting differs from the stored flag, any visibility transition delivered while any fullscreen is active is permanently swallowed: the flag now matches reality but applyVisibility() never ran. Note document.fullscreenElement is retargeted against the document, so it is non-null for ANY active fullscreen anywhere in HA (another card, kiosk-mode plugin holding body fullscreen), not just this card. Failure: with kiosk-mode/fullscreen active, every camera card that mounts gets its one initial IO record (isIntersecting=true) swallowed → flag=true, card never attaches → permanently black (and the setTimeout rescue path is dead per finding 1). Conversely a card scrolled out during fullscreen keeps streaming with no re-evaluation.

**What the standard says.** Fullscreen API: 'Let candidate be the result of retargeting fullscreen element against this; if candidate and this are in the same tree, return candidate' — document.fullscreenElement returns the retargeted (host-chain) element, so it is non-null for fullscreen elements inside shadow trees anywhere in the page (https://fullscreen.spec.whatwg.org/#dom-document-fullscreenelement). MDN IntersectionObserver.observe(): the callback fires once on the first render cycle after observe() and afterwards only on threshold crossings (https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/observe).

**Evidence.** webrtc-babycam.js:3181-3189: `const isIntersecting = entries[entries.length - 1].isIntersecting; if (this.isVisibleInViewport !== isIntersecting) { this.isVisibleInViewport = isIntersecting; if (document.fullscreenElement) return; this.applyVisibility(...); }` — state mutated, side-effect skipped, and no `fullscreenchange` handler exists in the file (grep: only fullscreenEnabled/fullscreenElement/requestFullscreen/exitFullscreen at 2060, 2936-2960, 3185).

### (refuted) pc.onremovestream handler relies on an API removed from the WebRTC spec — it can never fire in any current browser

**Original claim.** createPeer() assigns pc.onremovestream to clear call.remoteStream and dispatch a 'remotestream' event. The removestream event was removed from the WebRTC 1.0 specification and belongs to the pre-unified-plan model; Chrome removed Plan B (M93), Firefox never used it in unified-plan, and Safari never implemented the event at all, so this assignment is a no-op expando in every target browser and the code path is dead. Actual cleanup is (correctly) handled by the per-track 'ended' listeners added in ontrack, so nothing depends on it — but its presence suggests stream-removal is handled twice when only one path is real.

**Why it was refuted.** Code claim is accurate (custom_components/babycam/www/webrtc-babycam.js:1175-1181 assigns pc.onremovestream; track-'ended' cleanup at 1161-1170), but the standards claim's operative assertion — "can never fire in any current browser", "no-op expando", "dead code" — is false. mdn/browser-compat-data (api/RTCPeerConnection.json) lists Chrome removestream_event as version_added 24 with NO version_removed (deprecated only; Firefox removed at 60, Safari never). Chromium main branch (fetched 2026-07) still defines `attribute EventHandler onremovestream` in third_party/blink/renderer/modules/peerconnection/rtc_peer_connection.idl and still dispatches the event in rtc_peer_connection.cc DidModifyTransceivers — the unified-plan transceiver path, untouched by Plan B removal: `// Legacy APIs: "pc.onaddstream" and "pc.onremovestream". ... MaybeDispatchEvent(MakeGarbageCollected<MediaStreamEvent>(event_type_names::kRemovestream, previous_stream))` whenever a remote stream disappears after applying a remote description. So in Chrome/Edge the handler is a real IDL attribute that genuinely fires on renegotiation-removal. The finding's redundancy claim is also wrong: the same Chromium code MUTES (not ends) receiver tracks negotiated away ("Process the removal of a remote track" -> mute_tracks -> kReadyStateMuted), so the card's track-'ended' listeners do not cover that case and onremovestream is the only path clearing call.remoteStream there on Chromium. The recommended fix ("delete the handler") would therefore remove live cleanup, not dead code. Docs: https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/removestream_event (removed-from-spec part holds, but that alone doesn't make the handler dead).

### (refuted) canPlayUnmutedAudio() probe uses an invalid MP3 payload and the 'play' event as its success signal

**Original claim.** The probe's data URI (line 140) is not the claimed '1-second silent mp3': decoded it is 134 bytes — a single MPEG-1 Layer III frame header (FF FB 90 C4) whose header declares a 417-byte frame (i.e., truncated mid-frame, max 26ms even if complete) followed by garbage ASCII ('Xing-portify', 'mif1sudo', 'mif1vmrt', 'Corfe'). It is not a decodable silent second of audio in any engine. Separately, the probe resolves true on the 'play' EVENT (lines 146-149, 163): per spec that event fires merely because paused transitioned to false when play() runs its internal steps — before any data is fetched or decoded — so it never verifies that audio can actually render; when the bogus resource later fails, the element fires 'error' and rejects the pending play() promise with NotSupportedError, and the probe's correctness rests on the unguaranteed race that the queued 'play' task always beats the resource-failure task. An engine that surfaces the source failure first initializes unmuteEnabled=false even where unmuted autoplay is permitted, keeping every card muted until a gesture.

**Why it was refuted.** Payload facts verified true (decoded line 140 literal: 134 bytes, FF FB 90 C4 header declaring a 417-byte frame, truncated, ASCII garbage 'Xing-portify'/'mif1sudo'/'mif1vmrt'/'Corfe'; the line-139 comment is false) and the probe does resolve on the 'play' event (custom_components/babycam/www/webrtc-babycam.js:146-149,163). But the finding's actual defect claim — an "unguaranteed race" where an engine surfaces the source failure before 'play', yielding unmuteEnabled=false despite permitted autoplay — is wrong per the spec it cites. WHATWG internal play steps queue the 'play' event task synchronously during the play() call (before script yields); the dedicated media source failure steps that fire 'error' are queued only after resource selection's fetch/sniff, which awaits a stable state and cannot run until the script yields; both use the same media element event task source, which is FIFO (https://html.spec.whatwg.org/multipage/media.html). So 'play' deterministically precedes 'error' in every conforming engine — no race. When policy blocks, play() rejects NotAllowedError without firing 'play', and the .catch (line 166) resolves false. The probe therefore answers the autoplay-policy question correctly in both directions; the invalid payload never affects the result because the decision precedes decode. The claimed failure scenario and user impact cannot occur, leaving only a misleading comment and non-idiomatic (but spec-correct) detection pattern — hygiene, not a bug.

### (refuted) iOS Safari / HA companion-app WebView backgrounding suspends the page and pauses WebRTC audio; the card has no lifecycle handling for it and its auto-resume path only runs after foregrounding plus watchdog teardown

**Original claim.** On iOS, when Safari (or the WKWebView-based HA companion app) is backgrounded or the screen locks, page JavaScript (all setTimeout chains — the watchdog, image loop, stale monitors) is suspended and playback of a receive-only WebRTC MediaStream pauses; no 'freeze' event exists in WebKit and only 'pagehide'(app kill), media 'pause', and 'visibilitychange' fire around these transitions. The card cannot keep babycam audio playing in this state (documented platform limitation, acceptable per product constraints), but it also does nothing to make recovery prompt or clean: the media 'pause' handler's zero-delay auto-resume setTimeout (custom_components/babycam/www/webrtc-babycam.js:3664-3669) is queued and only executes on foregrounding, at which point the tracks/peer connection are typically dead after a long suspension, so the user gets the finding-1 sequence — watchdog wall-clock deadline expired → full teardown → reconnect — instead of an immediate deliberate restart on visibilitychange-to-visible. There is also no use of the documented partial mitigation: on iOS, pages actively capturing via getUserMedia (microphone two-way audio, which this card already supports via config.microphone) are kept running in background as calls, which the card could surface/leverage when background audio is essential.

**Why it was refuted.** The platform claim is true (iOS suspends timers and WebRTC playback in background; WebKit has no freeze event), but the defect claim is wrong. The card DOES have lifecycle handling and its recovery at foregrounding is already immediate: (1) visibilitychange is registered (custom_components/babycam/www/webrtc-babycam.js:3226) and documentVisibility→applyVisibility(true)→attachCard (3167-3179, 3072-3103, 622-668) re-attaches and calls play() on return-to-visible; (2) more decisively, the watchdog is a ≤1s-cadence setTimeout loop (549-561), so at foregrounding its long-overdue timer fires immediately — by the exact same queued-suspended-timer semantics the finding itself invokes for the pause handler's setTimeout at 3664-3669 — and that play() tick instantly detects Date.now() >= call.reconnectDate (any suspension >10s guarantees expiry since extendCallTimeout only adds RENDERING_TIMEOUT_MS=10000, line 36/519), tears down via endCall (which nulls state.activeCall, 1021-1023) and starts a fresh call on the next ≤1s tick (512-514). The finding's proposed fix, restartCall() on visibilitychange, is the same endCall+play sequence (575-592) and would save at most ~1 second of tick alignment — no material improvement. Worse, an eager visibilitychange restart risks tearing down a healthy shared call (one session per key serving multiple cards; short tab switches), which the current reconnectDate-validated design intentionally avoids: for short suspensions where tracks survive, the queued pause auto-resume (3664-3669) resumes playback with no teardown at all. The "watchdog deadline expired → teardown → reconnect" sequence the finding presents as the problem is in fact the prompt, clean, intended recovery, consistent with the never-stop-streaming/unbounded-reconnect and background-card invariants. Remaining substance (document that iOS cannot keep background WebRTC audio alive; optionally surface the getUserMedia keep-alive) is documentation advice, not a code defect.

### (refuted) End-of-candidates from the signaling channel is never delivered to the RTCPeerConnection

**Original claim.** When go2rtc signals end-of-candidates (webrtc/candidate with empty value), Go2RtcSignalingChannel maps it to oncandidate(undefined); the session handler logs 'Received end of ICE candidates' and calls addRemoteCandidate(undefined), whose first line `if (!candidate) return;` drops it. Per spec, end-of-candidates must be surfaced to the ICE agent via addIceCandidate with null/missing candidate or an empty candidate string. Never delivering it means the browser assumes remote gathering is still in progress: iceConnectionState cannot promptly reach 'failed' when no pair works (slowing the reconnect loop below the app's own 10s watchdog granularity) and 'completed' is unreachable, one of the two states isStreaming accepts.

**Why it was refuted.** The code and MDN claims are literally true (custom_components/babycam/www/webrtc-babycam.js:1256 drops falsy candidates; :4157 maps empty value to undefined; MDN confirms null/empty-string = end-of-candidates). But the triggering premise is false: go2rtc never sends webrtc/candidate with an empty value. Its pion OnICECandidate handler explicitly filters the nil end-of-gathering event (go2rtc pkg/webrtc/conn.go: `// last candidate will be empty; if candidate != nil { c.Fire(candidate) }`), and the WS sender (internal/webrtc/webrtc.go) only serializes non-nil candidates, which always yield non-empty strings. Go2RtcSignalingChannel is also the only channel in the file that ever invokes oncandidate (lines 4156-4158), so the falsy path is dead in practice — nothing is being dropped. Claimed impacts also fail: isStreaming (line 840) accepts 'connected' (the state actually reached), so 'completed' unreachability is inconsequential; and reconnect does not rely on ICE 'failed' — the play() watchdog (lines 471-563, reconnectDate/SIGNALING_TIMEOUT_MS=10s) recycles stuck calls in ~10s, faster than Chrome's ~15s ICE-failure timeout even with end-of-candidates delivered. Behavior is fine as-is.

### (refuted) go2rtc remote candidates synthesized with hardcoded sdpMid "0" — OperationError and silent candidate loss if the answer has no mid "0"
